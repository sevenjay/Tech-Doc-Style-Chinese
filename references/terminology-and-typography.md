# 術語與排版

僅在需要處理術語、錯詞、標點、留白或大小寫時讀取本檔案。所有規則只作用於可見正文，不作用於程式碼、路徑、欄位、命令、設定項和使用者指定的固定字面量。

## 術語原則

- 同一概念使用同一首選術語。
- 優先採用目標專案術語表和產品官方寫法。
- 不因為追求詞彙變化而替換同義詞。
- 詞語可能有多個合理含義時，先判斷語境，不做全域替換。
- 專案專屬術語放在目標專案的覆寫規則檔中。

## 空泛表達與黑話

以下詞語容易掩蓋具體動作。只有在有明確業務定義、屬於正式術語、引用原文或使用者要求保留時才使用：

- `賦能`
- `抓手`
- `閉環`
- `沉澱`
- `對齊`
- `對標`
- `拉通`
- `打通`
- `協同`
- `聯動`
- `洞察`
- `賽道`
- `心智`
- `調性`
- `戰役`
- `鏈路`
- `勢能`
- `兜底`
- `落盤`
- `收口`
- `透傳`

優先說明它實際指什麼：

- `賦能` -> `提供`，或直接寫明提供的功能
- `抓手` -> `關鍵措施`
- `閉環` -> `完整流程`，或列出開始、處理和完成條件
- `沉澱` -> `形成`、`積累`、`儲存`
- `對齊` -> `統一`、`確認一致`
- `拉通` / `打通` -> `連接`、`整合`
- `洞察` -> `分析結論`
- `兜底` -> 寫出失敗後具體的備援或保障機制
- `落盤` -> `寫入檔案`、`儲存到本地`
- `透傳` -> `原樣傳給下游`

以下詞語需視語境判斷，不應由檢查器自動替換：

- `場景`
- `生態`
- `體系`
- `路徑`
- `觸點`
- `卡點`
- `佈局`
- `矩陣`
- `顆粒度`
- `復盤`
- `梳理`
- `輸出`
- `提煉`

保留內部術語時，在首次出現處說明實際含義，避免連續堆疊多個術語。

## 標點

- 中文正文預設使用全形中文標點。
- 中文引號預設使用直角引號 `「」`；專案、地區、出版或引用規範可以覆寫此規則。
- 避免連續感嘆號、省略號和口號式斷句。
- 完整句式的清單項目統一使用句號；短語型清單項目可以不加句號，但同一清單保持一致。
- 並列詞語使用頓號，並列分句根據層級使用逗號或分號。
- 冒號後應有解釋、列舉或引用，不要把每句話都拆成冒號清單。
- 破折號、括號和斜線只在關係明確時使用，不用它們代替句子組織。

## 稱呼

- 技術文件預設不直接稱呼讀者，優先使用無主句或明確角色。
- 根據語境使用 `開發者`、`技術負責人`、`導入人員`、`業務負責人`、`產品經理`。
- `你`、`您`、`同學` 屬於風格提示，不是普遍語言錯誤；消費型產品、說明文字或品牌規範可以允許第二人稱。

## 中文與英文、數字之間的留白

在可見正文中，中文與可讀的半形英文單詞、英文縮寫、獨立數字和版本號之間通常保留空格：

- `取得批次 ID`
- `HTTP 請求`
- `版本 2.0`
- `AI 服務`
- `與 PM 協作`

不要機械處理：

- 行內程式碼和程式碼區塊
- JSON 鍵名
- URL 和 API 路徑
- 資料庫欄位名稱
- 命令、設定項、佔位符和正規表示式
- 直接對應 API 定義的表頭
- 產品官方拼寫和使用者指定字面量

數字排版還應檢查：

- 日期、時間和時區是否完整
- 百分比與百分點是否混用
- 數值是否帶有必要單位
- 區間上下界和包含關係是否明確
- 貨幣、溫度、儲存單位和千位分隔是否一致

## 技術術語大小寫

以下是常見推薦寫法，不應取代專案或產品的官方命名：

- `id` / `Id` -> `ID`
- `http` / `Http` -> `HTTP`
- `url` / `Url` -> `URL`
- `json` / `Json` -> `JSON`
- `api` / `Api` -> `API`
- `ai` / `Ai` -> `AI`
- `javascript` -> `JavaScript`
- `typescript` -> `TypeScript`
- `llm` / `Llm` -> `LLM`
- `aigc` / `Aigc` -> `AIGC`
- `rag` / `Rag` -> `RAG`
- `chatgpt` / `Chatgpt` -> `ChatGPT`
- `openai api` / `OpenAI api` -> `OpenAI API`
- `python` -> `Python`
- `nodejs` -> `Node.js`
- `github` -> `GitHub`
- `gitlab` -> `GitLab`
- `postgresql` -> `PostgreSQL`
- `grpc` -> `gRPC`
- `graphql` -> `GraphQL`
- `websocket` -> `WebSocket`
- `yaml` -> `YAML`
- `xml` -> `XML`
- `jwt` -> `JWT`

以下寫法需視語境判斷，只能提示人工確認：

- `JS`：簡短介面或既有名稱中可能合理，正式正文可寫 `JavaScript`
- `H5`：可能指行動 Web 活動頁，不等同於 HTML5 標準
- `Postgres`：可能是專案採用的正式簡稱
- `OAuth`：可能指通訊協定家族，不能自動補成 `OAuth 2.0`
- `k8s`：正式文件可寫 `Kubernetes`，命令、標籤和社群語境可能保留

## 常見錯詞與語境詞

可以作為確定錯誤處理：

- `閥值` -> `閾值`
- `佈署` -> `部署`
- `反回` -> `返回`
- `回朔` -> `回溯`
- `做為` -> `作為`
- `embeding` -> `embedding`
- `提示工程學` -> `提示工程`

必須結合語境判斷：

- `登入系統`，但可以說 `登陸月球`
- `設定參數`，但可以說 `配製溶液`
- `截至 4 月 12 日`，但可以說 `截止日期`
- `啟用功能`，但可以說 `起用新人`
- `識別欄位`，但可以說 `在圖中標示位置`
- 臺灣技術文件通常使用 `即時通訊`；`實時通訊` 多見於中國大陸用語
- `身分驗證` 表示確認身分，`授權` 表示授予權限

## 數量與邏輯

- `縮小了 3 倍` -> `縮小為原來的 1/3` 或寫明減少比例
- `從 20% 增加到 30%`：增加 10 個百分點，相對增加 50%
- `轉換率提升了 5%`：確認是提升 5% 還是 5 個百分點
- `翻了 1 倍` -> `變為原來的 2 倍`
- `不超過 100 以上` -> `不超過 100`
- `預計大約在 3 點左右` -> `預計 3 點左右`

修正表達時不得自行補充原文沒有的基數、年份、期限或測量結果。
